# Deploying Nocturne Library to AWS from scratch

This is the end-to-end, rebuild-from-nothing procedure for production: **AWS ap-south-1 + MongoDB Atlas M0 (AWS / Mumbai) + GitHub Actions CD**. Design and justification: [`ARCHITECTURE.md`](ARCHITECTURE.md). Script reference: [`infra/README.md`](../infra/README.md). Day-2 operations: [`RUNBOOK.md`](RUNBOOK.md).

Time: ≈ 1 hour the first time (Atlas 10 min, scripts 15–20 min, first image build/push 10–15 min, GitHub settings 10 min).

```
 1 tools + admin login      5 network (NAT EIP)        9 compute (ASG)
 2 Atlas cluster + user     6 IAM (role ARNs)         10 observability
 3 bootstrap (secrets)      7 security groups + ALB   11 smoke test
 4 GitHub environment/vars  8 first image push        12 CD takes over
```

## 1. Tools and an admin session

- AWS CLI v2, bash ≥ 4.4, Docker, git, curl (Windows: run the scripts from WSL or Git Bash).
- An AWS account with **IAM Identity Center** and a permission set with admin rights for the people who build infra. Never create IAM user access keys for this project.

```bash
aws configure sso --profile nocturne-admin      # region ap-south-1
export AWS_PROFILE=nocturne-admin AWS_REGION=ap-south-1
aws sso login && aws sts get-caller-identity
git clone https://github.com/VE-Vaniya/Nocturne-Library.git && cd Nocturne-Library
```

## 2. MongoDB Atlas M0 (free) in ap-south-1

1. <https://cloud.mongodb.com> → new project `nocturne` → **Build a database** → **M0 Free**, provider **AWS**, region **Mumbai (ap-south-1)** (keeps DB traffic in-region), name `nocturne`.
2. **Database Access** → add user `nocturne-app`, _password_ auth, autogenerated strong password, role _Read and write to any database_ (or scoped to `nocturnelibrary`). Avoid `'` in the password – the instance env file single-quotes values.
3. **Network Access**: leave empty for now. You add the NAT Elastic IP in step 5. Do **not** add `0.0.0.0/0`.
4. **Connect → Drivers** → copy the SRV string and insert the db name:
   `mongodb+srv://nocturne-app:<password>@nocturne.xxxxx.mongodb.net/nocturnelibrary?retryWrites=true&w=majority`

## 3. Bootstrap: ECR, secrets, buckets, alerts, budget

```bash
export BUDGET_EMAIL=team-alerts@example.com     # receives budget + alarm emails
./infra/00-bootstrap.sh
#   Value for MONGODB_URI (input hidden): <paste Atlas string>
#   Value for JWT_SECRET: <openssl rand -base64 48>
#   EMAIL_USER / EMAIL_PASS (Gmail app password) / GOOGLE_BOOKS_API_KEY: optional, Enter to skip
```

Confirm the **SNS subscription email** ("AWS Notification – Subscription Confirmation") or alarms will not reach you. Secrets go straight from the prompt to SSM SecureString; nothing is written to disk. To change one later: `./infra/00-bootstrap.sh --rotate JWT_SECRET` (then roll instances, step 12).

## 4. GitHub repository settings

**Environment** – Settings → Environments → **New environment `production`** → _Deployment branches and tags_: **Selected branches → `main` only** (optionally add required reviewers). The CD deploy job declares `environment: production`, so its OIDC token subject is `repo:VE-Vaniya@153434877/Nocturne-Library@1179123000:environment:production` (GitHub's immutable subject format: owner and repo IDs are appended for repositories created after 15 Jul 2026), which is exactly what the `gha-deploy` trust policy accepts – a workflow on any other branch cannot assume the role.

**Variables** (Settings → Secrets and variables → Actions → _Variables_; values are printed by the scripts in steps 6–7). They are not secrets – role ARNs and names only:

| Variable              | Example / source                                                      |
| --------------------- | --------------------------------------------------------------------- |
| `AWS_REGION`          | `ap-south-1`                                                          |
| `AWS_DEPLOY_ROLE_ARN` | `arn:aws:iam::<acct>:role/gha-deploy` (`20-iam.sh`)                   |
| `AWS_CI_ROLE_ARN`     | `arn:aws:iam::<acct>:role/gha-ci` (`20-iam.sh`, only if CI reads ECR) |
| `ECR_REGISTRY`        | `<acct>.dkr.ecr.ap-south-1.amazonaws.com`                             |
| `ASG_NAME`            | `nocturne-asg`                                                        |
| `CONFIG_BUCKET`       | `nocturne-config-<acct>-ap-south-1` (deploy re-uploads compose files) |
| `APP_URL`             | `http://<alb-dns>` (`40-alb.sh`; used by the smoke test)              |

If the workflow files use different names, match them – the scripts' env contract is `AWS_REGION`, `ASG_NAME`, `CONFIG_BUCKET`, SSM `/nocturne/prod/image_tag` and `/nocturne/prod/previous_image_tag`.

**Secrets**: only third-party tokens the CI stages need (e.g. `SONAR_TOKEN`, `SNYK_TOKEN`). **No AWS keys** – AWS access is OIDC only.

**Branch protection** on `main` (required by the brief): require PRs + 1 approval, require all CI status checks, block force pushes.

## 8. First image push (one time, manual)

Instances refuse to start until `/nocturne/prod/image_tag` names images that exist, so push the first release by hand (afterwards CD does it on every merge to `main`):

```bash
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REG=$ACCOUNT.dkr.ecr.ap-south-1.amazonaws.com
SHA=sha-$(git rev-parse --short=7 HEAD); VER=v0.1.0
aws ecr get-login-password | docker login --username AWS --password-stdin "$REG"

docker build -t "$REG/nocturne-frontend:$SHA" -t "$REG/nocturne-frontend:$VER" .
docker build -t "$REG/nocturne-backend:$SHA"  -t "$REG/nocturne-backend:$VER"  ./backend
for img in nocturne-frontend nocturne-backend; do
  docker push "$REG/$img:$SHA" && docker push "$REG/$img:$VER"
done

aws ssm put-parameter --name /nocturne/prod/image_tag --type String --overwrite --value "$SHA"
```

Images are x86_64 (`t3` instances); on Apple Silicon add `--platform linux/amd64`. Tags are immutable – a second push of the same tag fails by design; bump the version instead. Screenshot ECR → repositories → images (both tags) for the submission.

## 9. Compute

```bash
./infra/50-compute.sh --wait    # uploads compose + agent config, launch template, ASG 2/2/4; waits for 2 healthy targets per TG
```

If it times out: Session Manager into an instance (EC2 → instance → _Connect_ → _Session Manager_) and `sudo tail -100 /var/log/nocturne-bootstrap.log`, or read log group `/nocturne/prod/bootstrap`. Common causes: Atlas access list missing the NAT EIP (readiness warning only), `image_tag` wrong, a missing SSM parameter.

## 12. Continuous delivery from here on

On every merge to `main`, the CD workflow (pipeline stages 11–12, owned in `.github/workflows/`):

1. assumes `gha-deploy` via OIDC (`environment: production`), builds + Trivy-scans both images, pushes `sha-<short>` and `vX.Y.Z` to ECR;
2. runs `scripts/deploy.sh sha-<short>` → `previous_image_tag ← image_tag`, `image_tag ← new`, compose files re-uploaded, **ASG instance refresh** (Rolling, MinHealthyPercentage 50, InstanceWarmup 120) and waits; the ALB keeps ≥ 1 healthy instance serving throughout (rolling, no downtime);
3. runs `scripts/smoke-test.sh "$APP_URL"`; on failure runs `scripts/rollback.sh` (→ `previous_image_tag`) and fails the job.

Manual operations (same scripts, admin or `gha-deploy` credentials):

```bash
scripts/deploy.sh v0.2.0                 # deploy a specific tag
scripts/rollback.sh                      # back to previous_image_tag
scripts/rollback.sh sha-1a2b3c4          # any tag still in ECR (lifecycle keeps the newest 20)
scripts/deploy.sh --refresh-only         # roll instances without changing the tag (e.g. after rotating a secret)
```

The manual GitHub _rollback_ workflow (`workflow_dispatch`, input `image_tag`) calls `scripts/rollback.sh <tag>`.
